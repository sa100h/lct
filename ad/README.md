# ad — Samba AD Domain Controller

Каталог контроллера домена Samba (база `nowsci/samba-domain`). Нужен для аутентификации
пользователей по LDAP/LDAPS: диспетчеры, техники и администраторы логинятся в приложение
по учёткам домена `lct.ru`.

## Что делает `ad/custom.sh` (оркестратор запуска)

По шагам (всё видно в `docker logs lct-ad-1`):

1. Запускает штатный `init.sh` из образа в фоне (провижининг домена → supervisord).
2. Ждёт, пока Samba ответит по LDAP (`ldapsearch` по порту 389, до 5 мин).
3. Ждёт появления `smb.conf`.
4. Проверяет TLS-сертификат в `/var/lib/samba/private/tls` — при отсутствии,
   истечении срока или отсутствии SAN выпускает самоподписанный сертификат
   сервера на 365 дней для `AD_TLS_HOSTNAME` (по умолчанию `dc1.lct.ru`).
   Публичная часть копируется в отдельный том `ad_public_certs`; приватный
   ключ остаётся только в томе AD.
5. Обновляет в `[global]` секции `smb.conf` параметры TLS
   (`tls enabled/certfile/keyfile/cafile`), сохраняя первоначальную копию `.bak`.
6. Перезапускает Samba и проверяет LDAPS рукопожатие, сертификат и имя сервера.
7. Включает `ldap server require strong auth = yes`: обычный простой bind без
   TLS на порту 389 Samba не принимает. Порт 389 не публикуется наружу Compose.
8. Выполняет идемпотентный `ad/init/01-users-groups.sh` для тестовых
   пользователей, групп и сервисной учётной записи `lct-app-bind`.
9. Удерживает процесс живым (`wait` на `init.sh`).

## Что создаёт `ad/init/01-users-groups.sh`

| Тип | Имя | Группа |
|-----|-----|--------|
| user | `admin.test` | `Admins` |
| user | `technik.test` | `Technics` |
| user | `dispetcher_ods` | `Dispetchers_ODS` |
| user | `dispetcher_rayon` | `Dispetchers_rayon` |

OU: `Users`, `Groups`, `ServiceAccounts`. Пароли пользователей хардкожены в скрипте
(демо-стенд) — при деплое заменить на реальные значения.

`lct-app-bind` создаётся в `OU=ServiceAccounts` с паролем из `AD_BIND_PASSWORD`.
Учётная запись не входит в административные группы. Будущий адаптер `app-service`
использует её для чтения состояния и групп пользователя при refresh без пароля
пользователя. Самих LDAP-запросов в `app-service` пока нет: login и refresh
возвращают 503 до подключения адаптера.

## Настройки (`.env`)

| Переменная | Значение по умолчанию | Назначение |
|------------|----------------------|------------|
| `DOMAIN` | `lct.ru` | Доменное имя AD-домена |
| `DOMAINPASS` | `ChangeMeNow!2024` | Пароль `Administrator` домена (политика сложности Samba) |
| `AD_BIND_PASSWORD` | обязателен | Пароль сервисной учётной записи `lct-app-bind` |
| `AD_TLS_HOSTNAME` | `dc1.lct.ru` | Имя LDAPS сервера в сертификате и Docker-сети |
| `HOSTIP` | `172.18.0.3` | IP хоста Docker для DNS-записей |
| `DNSFORWARDER` | `127.0.0.11` | Форвардер DNS (embedded DNS Docker) |
| `JOIN` | `false` | `false` — создать новый домен, `true` — присоединиться к существующему |

## Порты

| Порт | Протокол | Назначение |
|------|----------|------------|
| 53 | tcp+udp | DNS домена |
| 389 | tcp | LDAP для внутренних задач Samba; простой bind без TLS запрещён |
| 636 | tcp | LDAPS — основной протокол клиентов |
| 88 | tcp+udp | Kerberos |

## Экземпляр / storage

Объём `ad_data` хранит состояние домена, `ad_config` — конфиги. Отдельный
`ad_public_certs` содержит только публичный сертификат для `app-service`.
После `docker compose down -v` домен будет провижинен заново; `objectGUID`
пользователей изменятся и больше не будут соответствовать локальным `users.id`.

## Локальный запуск

```bash
docker compose up -d ad
docker logs -f lct-ad-1          # следим за оркестрацией
docker compose exec ad bash -lc 'LDAPTLS_CACERT=/ad-public-certificates/ldaps.pem \
  ldapsearch -x -H ldaps://dc1.lct.ru:636 -D "lct-app-bind@lct.ru" -W \
  -b "dc=lct,dc=ru" "(sAMAccountName=admin.test)"'
```

В контейнере `app-service` публичный сертификат доступен по
`/run/certs/ldaps.pem`; имя `dc1.lct.ru` добавлено как сетевой alias `ad`.
При будущем подключении LDAP адаптера сертификат нужно проверять вместе с
именем сервера. Отключать TLS проверку для тестового стенда не требуется.

Самоподписанный серверный сертификат удобен для одного тестового контроллера:
клиент доверяет ровно файлу `ldaps.pem` из общего тома. При перевыпуске нужно
убедиться, что все клиенты получили новую публичную часть. Для нескольких
контроллеров удобнее внутренний CA с отдельными серверными сертификатами;
внешний CA имеет смысл при уже существующей инфраструктуре сертификатов.
