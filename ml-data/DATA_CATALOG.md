## 0. Конвейер одним взглядом

```
ext-journal-<год>.7z  (~1.7 ГБ на год, 2019–2026, сырые журналы АСПИ)
        │  распаковка
        ▼
extracted/            (15 ГБ CSV, по годам; колонки: дата, время,
        │  агрегация по (канал, день[, час])        ид_канала_данных,
        │  + фильтры + EXCLUDE_SPANS                 значение_датчика,
        ▼                                            тревожный)
agg/agg-<год>.parquet     daily    (38 колонок)   справочники:
agg/agg-hour-<год>.parquet  hourly (39 колонок)   каналы (11 487), объекты (95)
        │  rolling-окна строго до дня t (anti-leak), календарь,
        │  состояния, переходы, hour-профиль
        ▼
features/features-<категория>.parquet   (201–202 колонки = 197–198 фич, 4 кат.)
features/features-<категория>-latest.parquet  (sidecar: последняя строка на канал)
        │  train <2026 / test =2026, LightGBM (scripts/train.py)
        ▼
ml-service/models/<категория>/model.lgb + meta.json
```

Каждый шаг **воспроизводим скриптом** (команды в §5). Ни один файл не
генерируется "вручную".

## 2. Дневная агрегация — `agg/agg-<год>.parquet`

**Зерно (гранулярность):** 1 строка = (канал, день), только дни, когда
канал что-либо эмитировал. 39 колонок.

| Колонка | Тип | Смысл |
|---|---|---|
| `channel` | string | ид канала данных |
| `day` | string | дата `YYYY-MM-DD` |
| `n_events` | int32 | всего событий канала за день |
| `n_alarm` | int32 | событий с `тревожное=true` |
| `n_num` | int32 | событий с числовым значением |
| `n_fault1970` | int32 | событий с артефактом `01.01.1970 03:00:0x` — сбились часы АСПИ; организаторы: трактовать как состояние «неисправность» (добавлено 2026-09-24) |
| `num_sum / num_sumsq / num_min / num_max` | float | статистики значений (через sum и sumsq фичи строят mean/var) |
| `s_0 … s_25` | int32 | количество событий каждого из 26 состояний словаря за день |
| `cabinet` | dict(string) | шкаф канала |
| `ид_объект` | dict(string) | объект канала |

**Семантика значений (ответы организаторов, 2026-09-24, см.
`справочник_состояний.csv`):** число у газовых датчиков — % объёма метана
(порог тревоги 1%, 5–15% — полоса воспламенения); значения вне физической
полосы и артефакты 1970-го — неисправность, в num_* не попадают (invalid
mask).

Объём: 533 049 (2019) → 686 322 (2020) → 555 301 (2021) → 538 850 (2022) →
545 656 (2023) → 505 007 (2024) → 574 627 (2025) → 324 978 (2026) строк;
4.32 М строк суммарно. Каналов в году: 5 622 (2019) → 11 447 (2026) —
сеть растёт год от года. 4 МБ на год (2 МБ — неполный 2026).

## 3. Часовая агрегация — `agg/agg-hour-<год>.parquet`

Добавлена 2026-09-18. **Зерно:** 1 строка = (канал, день, час).
Тот же набор колонок, что у daily, + `hour` (int32, 0–23; по конвенции
`-1` = событие без поля `время` — на практике за 2019–2026 таких строк 0).
Строки эмитятся только там, где в этом часу были события — без
нулевого заполнения 24 часов.

Объём: 1 791 751 (2019) / 2 149 203 (2020) / 2 590 578 (2021) / 2 056 972
(2022) / 1 843 717 (2023) / 2 008 715 (2024) / 2 141 815 (2025) / 1 190 221
(2026); 15.8 М строк суммарно. ~16–21 МБ на год.

**Сверка:** сверка с daily-агрегацией скриптом
`scripts/_reconcile_hour.py` — сворачивание по (channel, day) совпадает с
`agg-<y>.parquet` по всем счётчикам **на 100 %** (0 расхождений по всем 8 годам).

## 4. Фичевые таблицы — `features/features-<категория>.parquet`

**Зерно:** 1 строка = (канал, день) внутри наблюдаемого охвата канала.
Колонки: `channel`, `day`, `year`, `label` + **197 фич** (198 для fire-risk).
**Всё в строке дня t построено строго из данных до t** — горизонта
`t` не затрагивается (anti-leak, см. §6).

### 4.1 Метки (label = 1)

Общее правило для **всех** категорий: `label = 1`, если на день t было
(а) тревога (`тревожное=true`) ИЛИ (б) хотя бы одно **критическое для категории**
состояние (набор `critical` из `vocab.json`) в день t. Каналы берутся по
категории (`CATS`):

| Категория | Каналы | Особое |
|---|---|---|
| sensor-failure | **все** каналы | — |
| fire-risk | Пожарная охрана, Температурная, Газовая охрана | критическое состояние засчитывается **только если началось в день t** (не было критическим на t-1) — иначе 99.7 % положительных были бы "продолжением" длинного состояния и задача вырождалась в «было критически вчера». Плюс фича `rep_gap` (дней с последней отчётности) |
| unauthorized-access | Охранная подсистема | — |
| infrastructure-wear | Диспетчерский контроль, Диагностическая подсистема | — |

Гранулярность: строка «канал × день, когда канал активен»; каналы с дежурной
активностью дают много строк → высокий `positive rate` (см. прим. ниже).

### 4.2 Группы фич (197/198)

| Группа | Колонки | Смысл |
|---|---|---|
| Активность, окна 7/14/30 д | `e7 a7 e14 a14 e30 a30` | события/тревоги за последние 7/14/30 дней до t |
| Числовые значения | `n7 m7 s7 n14 m14 s14 n30 m30 s30` | счётчик/среднее/стандартное отклонение значения датчика за окно |
| Плотность активности | `act7 act14 act30`, `ar7 ar14 ar30` | **дни** с активностью / с тревогами за окно |
| "Тишина" | `since_act`, `since_alar` | дней до последней активности / последней тревоги |
| Разнообразие | `div30` | число различных состояний за 30 дней |
| Календарь | `month_sin`, `month_cos`, `dow` | сезонность (время года, день недели) |
| Статика | `cabinet`, `object_code`, `ch_age` | шкаф, объект, "возраст" канала в сети |
| Состояния | `t7_0..25`, `t30_0..25` (52) | доля каждого из 26 состояний за 7/30 дней |
| Переходы состояний | `tr7_0..25`, `tr14_0..25` (52) | число переходов в каждое состояние за 7/14 дней (сдвиг до t, без same-day) |
| Fire-risk только | `rep_gap` | дней с момента последней отчётности канала (каденс) |
| **Hour-профиль (2026-09-19)** | `e7h_0..23`, `a7h_0..23`, `night_share7`, `peak_share7` (50) | события/тревоги по часам за 7 дней до t; доля событий ночью (00–05) и днём (08–20) — из `agg-hour-<y>.parquet` |

### 4.4 Sidecar «последняя строка на канал» — `features-<кат>-latest.parquet`

Рядом с каждой фичевой таблицей лежит маленький **sidecar**: одна строка на
канал — его наблюдение на `max(day)`. Сервис читает именно его
(`LagStore.latest_features_for`), чтобы не сканировать 36 МБ паркета на каждый
`/predict`: оттуда берутся «базовые» фичи, а 11 лагов считаются по истории.
Число строк = число каналов категории: 11 482 / 6 830 / 2 209 / 2 443.

Пересобирать **после каждого** прогона `feature_engine`:

```bash
./.venv/bin/python -m scripts.build_latest_sidecars            # все 4 категории
./.venv/bin/python -m scripts.build_latest_sidecars --check    # только проверка
```

Скрипт возвращает код 1, если sidecar отсутствует, не покрывает набор фич
модели или отстал от `max(day)` фичевого паркета.

Почему это отдельный шаг, а не «само построится»:

* **отсутствует** — `LagStore` строит его на месте, но в контейнере данные
  смонтированы read-only (`./ml-data:/app/data:ro`), поэтому запись падает;
* **устарел** — сервис молча кормит модель старым снимком. Так уже было
  2026-09-29: два sidecar'а отставали от пересборки фич на 3 дня и вообще не
  содержали `f7`/`f30`, поэтому эти фичи подставлялись как `0.0`, хотя модель
  обучалась на реальных значениях.

После пересборки — перезапустить ml-service, чтобы он перечитал файлы.

## 6. Гарантии качества (что проверено)

1. **Anti-leak метки.** Аудит `scripts/audit_leak.py`: модели, обученные на
   подмножестве фич с `since_alar == 0` (без "свежих" сигналов), дают
   AUC ≈ 0.50 (0.496–0.531 по 4 категориям на 2026) — т.е. без фич,
   построенных на "современном" окне, метка предсказывать **невозможно**;
   с фичами — см. §7. Часовые фичи (`e7h_*`, `a7h_*`) тоже в этом аудите:
   leak не вносят.
2. **Hour-агрегат сверен** с daily на 100 % по всем 8 годам (`_reconcile_hour.py`).
3. **Hour-фичи сверены** прямым пересчётом из `agg-hour` — значение к
   значению (smoke `scripts/_smoke_hour_features.py`), первые дни канала —
   нулевой профиль (leak невозможен по построению).
4. **Сплит:** train = годы < 2026, test = 2026 (будущее). Никакого
   кросс-временного перемешивания.

## 7. Модели и их качество (test = 2026, <t>2026)

Исторический градиентный бустинг (sklearn `HistGradientBoostingClassifier`:
300 итераций, lr=0.08, 31 лист, l2=1.0, `class_weight="balanced"`, seed=42).
`ml-service/models/<кат>/model.joblib` + `meta.json` (метрики, список фич).

| Категория | train → fit | test | AUC | AP | P@0.5 | R@0.5 |
|---|---|---|---|---|---|---|
| sensor-failure | 2.28 М → 1.0 М | 180 182 | **0.957** | **0.991** | 0.983 | 0.892 |
| unauthorized-access | 406 234 | 28 721 | **0.897** | **0.981** | 0.957 | 0.848 |
| infrastructure-wear | 570 724 | 39 808 | 0.800 | 0.772 | 0.725 | 0.676 |
| fire-risk | 112 443 | 36 432 | 0.508 | 0.373 | 0.322 | 0.143 |

Честный разбор:
- **sensor-failure и unauthorized-access** — производственные качества.
- **infrastructure-wear** — средний; есть место, но потолок данных, похоже,
  достигнут.
- **fire-risk** — слабый сигнал (AUC ≈ 0.51): "новый пожарный инцидент"
  предсказывается на этой дневной агрегации почти на уровне случайного.
  Для улучшения нужна новая сырьё (более тонкая гранулярность, кросс-канальная
  пространственная зона, другой label). Часовые фичи, добавленные 19.09,
  не дали прироста на этой метке (метрики 134-фичевой и 184-фичевой
  схем совпадают с точностью 4 знака).

## 9. Что это даёт команде при оценке ML-сервиса

- **4 задачи** с готовыми обученными моделями; качество разделено: 2
  сильные, 1 средняя, 1 слабая (fire-risk — открытая задача).
- **Данные прозрачны**: у каждой строки — канал, день, метка, все фичи;
  можно открыть `features-<cat>.parquet` и вручную объяснить предсказание.
- **Воспроизводимость**: любой артефакт строится одной командой (§5);
  revert при необходимости — бэкапы в §8.
- **Анти-leak подтверждён** аудитом (§6 п.1), а не декларацией.
